# DUO sign-in bridge and future Arcade integration

This change adds only DUO account sign-in, not the Arcade screen. `duo-sso.js` is mounted once in `backend-server.js` using existing `requireAuth` and `dbGetUserById`. The dedicated consent page is `public/duo-connect.{html,css,js}`. No database changes or existing Profile UI edits are required.

Set `DUO_REDIRECT_URIS` to the exact deployed DUO callbacks for `/auth/chainlens/callback`, `/auth/google/callback`, and `/auth/discord/callback`. A comma-separated allowlist can include exact localhost callbacks for development. Set DUO's `PUBLIC_ORIGIN`, `CHAINLENS_ORIGIN` and `CHAINLENS_SHARED_LOGIN=1` accordingly. The bridge is unavailable for callbacks outside this allowlist. Existing ChainLens login/account creation and `FRONTEND_URL` must be configured normally. This code is local and uncommitted; production activation requires deployment/configuration of both applications.

The user's existing ChainLens Google/Discord credentials and callbacks are configured in the local ChainLens `.env` (values were not printed/copied). DUO reuses those flows through `login_provider=google|discord` on `/auth/duo`. The consent page opens the matching existing `/auth/google` or `/auth/discord` when signed out, and all three buttons resolve the same ChainLens account subject. The only permitted hints are Google/Discord; arbitrary hint values are ignored. No ChainLens JWT secret is copied into DUO. The live site still serves HTML fallback for the bridge URLs, so deployment remains necessary; DUO detects this and explains the pending bridge rather than redirecting into an unrelated page.

The Arcade can link to DUO's public origin or to `${DUO_ORIGIN}/auth/chainlens` for account sign-in. This redirects to ChainLens `/auth/duo`, then the consent page. A signed-out user opens the existing Profile sign-in/create-account flow in another tab. The consent tab observes `cl_token` storage/focus changes, checks the local authenticated profile, and asks the user to continue. The user's existing ChainLens session token stays on the ChainLens origin.

`POST /api/duo/authorize` requires the existing authenticated account, client ID `duo`, exact callback, random state and S256 PKCE challenge. It issues a one-minute code. DUO exchanges it at `POST /api/duo/token` with the verifier and same callback, then reads `GET /api/duo/userinfo` with a one-use, one-minute access token. Both code and token are consumed; failed exchange attempts also consume the code. The game-chat extension also supplies a limited `game_chat_token` alongside `{sub: accountId, name: displayName}`. It remains in the DUO server session and can authorize game-room chat/public pictures and explicit friendship aliases, using a separate signing key and audience. Friendship aliases reuse the existing eligibility, ownership and block checks; general account/wallet endpoints remain inaccessible. See [GAME-CHAT.md](GAME-CHAT.md). Email, wallets, holdings and private profile fields are excluded. This is not a general-purpose OAuth provider: new Arcade clients need separate client binding/allowlists.

The full integration/verification notes are also at `C:/Users/balla/Documents/DUO/docs/LOGIN-AND-ARCADE.md`. DUO includes DUO/SOLO/SURVIVAL/ROULETTE, all eleven custom card styles, server-side Quick play and open/locked lobbies. Normal public links avoid third-party-cookie and wallet-injection problems; iframe embedding is not part of this work.

Future cosmetic token gating must be verified on the server against wallet ownership and holdings, with a minimal expiring entitlement contract. A ChainLens account alone, an attached watch-only address or a client-reported balance is not an entitlement. No token-gating policy was enabled by this change.

Validation: `node --test test/duo-sso.test.js` covers callback allowlist, authentication, PKCE, private-field exclusion, expiry and replay rejection. A separate two-server Playwright harness exercised the consent page with a stub account store and established a real DUO session. Production users/accounts and real provider credentials were not touched. Follow agent-handoff and preserve existing dirty Profile UI/e2e changes.
